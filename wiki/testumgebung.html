Testumgebung ohne Hardware

Solange MOROS.neo, IO-Module und Leser fehlen, läuft alles in Docker auf dem Mac. Der Mac (Apple Silicon) hat dieselbe Architektur (arm64) wie der MOROS.neo. Der Simulator spricht echte Protokolle (Modbus TCP, serielle Textzeilen über TCP), deshalb laufen die echten Treiber und nicht nur Attrappen.

Bedienung

docker compose up --build        # alles starten
docker compose run --rm app pytest  # Tests
docker compose down -v           # alles inkl. DB löschen
AdresseZweck
http://localhost:8000/Display (Kiosk), Live-Chipanzeige
http://localhost:8000/adminFachübersicht, Testöffnung (noch ohne Login)
http://localhost:8081/Simulator: Chips vorhalten, Türen schließen, Nothebel, Modul aus

Display-Größe wie WP10A testen: Chromium mit --kiosk --app=http://localhost:8000/ oder DevTools-Gerätemodus.

Was der Simulator nachbildet

  • Schloss entriegelt nur bei Impuls ≥ 1000 ms (Kerong), einmal pro Impuls.
  • Feder drückt die Tür auf → Schalter meldet „offen“. Nach 8 s schließt die Tür automatisch (SIM_TUER_ZU_NACH_S, 0 = nur manuell).
  • Ausgang länger als 5 s an → Fehlermeldung „Spule überhitzt“ im Log.
  • „Modul aus“: Modul antwortet nicht mehr (Timeout wie bei gezogenem Kabel).
  • Testchips: 04A1B2C3D4/D5/D6 (Anna, Bernd, Clara), DEADBEEF (unbekannt).

Unterschiede zum Automaten

  • IO-Module: im Simulator ein Host mit Ports 5021–5023, am Automaten 192.168.10.11–13 Port 502. Steht nur in Tabelle io_modul.
  • Leser: MVT_LESER_URL=socket://hwsim:7000 statt /dev/ttyS0.
  • App und Datenbank laufen hier getrennt. Auf dem MOROS.neo laufen sie gemeinsam in einem LXC-Container. Den gibt es auch auf dem Mac: deploy/boottest.sh → http://localhost:8002/ (siehe deploy/README.md).
